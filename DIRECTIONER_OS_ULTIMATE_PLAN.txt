M. WHAT THE OS NEEDS FROM THE BEYONDERS BACKEND  (REQUESTS, not claims)
--------------------------------------------------------------------------------
Aditya's backend notes were not available when this was written (A4). Treat
everything below as the OS's REQUIREMENTS. When beyonders-platform-backend is
handed over, the OS agent maps each item to what exists (TODO 150/199/200),
marks gaps, and the backend agent decides what to build. Nothing here says the
backend already does any of it.

M0. Platform-wide
  M0.1 Versioned HTTPS API (/v1/...), published OpenAPI spec, stable error
       schema (code, message, request_id, retry_after).
  M0.2 A sandbox/staging environment and test accounts that the OS test
       harness can use (no production data in CI).
  M0.3 Rate-limit headers on every response (limit, remaining, reset).
  M0.4 Idempotency-Key support on mutating calls.
  M0.5 Deprecation policy and a /v1/meta endpoint (min client version,
       maintenance notices, feature flags).
  M0.6 Health/status endpoint usable for offline-vs-outage detection.
  M0.7 Region/data-residency stance stated in writing.

M1. Identity and auth
  M1.1 OAuth2 device authorization grant (device_code, user_code, interval,
       slow_down) for headless/terminal/OS login.
  M1.2 Authorization-code + PKCE (S256) for browser login with loopback
       redirect.
  M1.3 Short-lived access tokens; rotating refresh tokens with reuse
       detection; revocation endpoint; token introspection or JWKS for
       offline verification of entitlement blobs.
  M1.4 Audience-scoped tokens (os, cli, aria, cloud, update) via token
       exchange so one login serves CLI, Aria and OS with least privilege.
  M1.5 MFA/passkey support in the web flow; account recovery rules.
  M1.6 Account deletion and data-export endpoints.
  M1.7 Session list per account.

M2. AI proxy (text/agent)
  M2.1 Streaming chat/completions-style endpoint (SSE) with cancel; tool-call
       passthrough; request size limits. Whether it is OpenAI-compatible is the
       backend's choice - OS needs the spec either way.
  M2.2 Model aliases resolved server-side (e.g., the rebrand names); the OS
       never sees provider names or keys.
  M2.3 Per-account quota and rate-limit with clear 429 semantics, plan info,
       and a "degrade to smaller model" signal if the backend supports it.
  M2.4 Usage metering endpoint (read) so the OS can show remaining quota.
  M2.5 Server-side prompt-injection and abuse controls are the backend's; the
       OS adds its own (D9/D10) and does not rely on them.
  M2.6 Clear data-handling statement: prompt retention, training use, logs.

M3. Voice proxy (for Aria)
  M3.1 Streaming STT endpoint (WebSocket or gRPC): audio framing, sample
       rate, chunk size, partial/final transcripts, end-of-utterance.
  M3.2 Streaming TTS endpoint: voice ids, chunked audio, cancel/barge-in.
  M3.3 Latency telemetry fields (opt-in) to tune the pipeline.
  M3.4 Same auth/quota model as M2; separate meters.
  M3.5 Statement that raw audio is not retained (or what is) - in writing.

M4. Cloud storage
  M4.1 Blob API for client-side-encrypted chunks: content-addressed or
       id-addressed put/get/head/delete, resumable and chunked, with
       integrity checksums.
  M4.2 Manifest/version API (list, history, restore, delete) that never needs
       plaintext or keys.
  M4.3 Quotas and usage endpoints; over-quota error semantics.
  M4.4 Multi-device change feed (cursor-based) for sync.
  M4.5 Deletion semantics and retention windows stated.
  M4.6 Optional: sharing primitives (deferred; E2E complexity).

M5. Device registry
  M5.1 Register/list/rename/revoke devices; device-bound refresh tokens.
  M5.2 Optional attestation intake (TPM quote) - default off.

M6. Entitlements
  M6.1 Read-only entitlements endpoint: plan, features, quota, reset time,
       signed blob with expiry for offline grace.
  M6.2 (Billing UI/payment is NOT an OS task; the OS only displays status.)

M7. Updates and channels
  M7.1 Channel manifest (stable/beta/dev): which image tag/digest to follow.
  M7.2 Minimum-version/forced-update signals for security fixes.
  M7.3 Where signed images live is a separate decision (467).

M8. Telemetry and crash intake (opt-in only)
  M8.1 Intake endpoints with an explicit schema; rotating random install id;
       server-side deletion by id.
  M8.2 Crash report intake accepting scrubbed bundles; size limits.

M9. Notifications
  M9.1 Optional push/poll for account notices (quota nearly used, security
       alert). Must work without a persistent open connection by default.

M10. Security expectations from the backend
  M10.1 TLS 1.2+ only; HSTS; certificate rotation plan communicated (OS
        decides on pinning in TODO 123).
  M10.2 Signing keys for entitlements/manifests under backend control; public
        keys/JWKS retrievable; rotation overlap.
  M10.3 Abuse/rate controls for token endpoints.
