--------------------------------------------------------------------------------
CC1  "Complete" means finished end to end: code + service wiring + GUI surface +
     docs + a real-effect test (RET, rule RR1) that passed on main in CI, with
     the evidence committed. A task with no GUI surface (when it is user-facing)
     is NOT complete (see GP1).
CC2  NO STUBS: no `todo!()`, `unimplemented!()`, `// TODO`, `pass`-bodies,
     hard-coded fake data, "coming soon" screens, or disabled buttons presented
     as working. A CI step (`dos-nostub`, U348) greps and fails
     the build on them outside tests and files labeled SCAFFOLD.
CC3  HONEST STATUS: use NOT-STARTED / SCAFFOLD / REAL-PARTIAL / REAL-DONE only.
     If something cannot be completed in your environment (no KVM, no network,
     cargo missing, upstream bug), write the exact blocker + smallest next step
     (RR10) and mark UNVERIFIED. Never claim "done" to move on.
CC4  RUN-ALL MODE. Aditya may write `run all` (or `run M13-M16`). Then:
     work milestone by milestone in order, commit directly on main in small
     commits, STOP at the first red RET or at any OWNER-AUTH gate, and write a
     status block to docs/plan-status.md so a fresh session can resume exactly
     there. This replaces the one-task-per-session rhythm (RR7) for that range
     only. Boundaries B1-B14 and the restricted-file rule never relax.
CC5  CONTEXT HYGIENE FOR LONG RUNS: after every milestone, write
     docs/handoff/<milestone>.md (what changed, commands to re-verify, open
     blockers). A new session starts by reading plan-status.md + the latest
     handoff.
CC6  QUALITY BAR BEFORE EVERY PUSH: fmt, clippy -D warnings, tests, `dos-nostub`,
     `dos-purge-scan` (once U429 exists), QML lint (qmllint), shellcheck, and the
     RET for the touched task. Red -> fix before pushing; never push red.
CC7  NO SCOPE SHRINKING: if a task looks too big, split it into smaller tasks
     in plan-status.md and keep every piece, rather than silently doing less.
CC8  Visual work is judged by screenshots, not by "it compiled": each GUI task
     attaches before/after screenshots (dark + light) from the booted image.
CC9  PERFORMANCE SANITY: record numbers (boot time, idle RAM, frame time) in

V4-B. GUI PARITY RULE (GP)  - "if it exists in code, a human can use it in the GUI"
--------------------------------------------------------------------------------
GP1  Every user-facing capability, daemon and setting gets a graphical surface
     reachable by mouse/touch/keyboard with no terminal. The CLI/`dosctl` is a
     power-user alternative, never the only way.
GP2  Parity is measured, not claimed: `dos-parity` (U347) joins the capability
     catalog + daemon list against a GUI route table and prints the gaps. CI
     fails if a REAL catalog entry has no GUI route.
GP3  Every GUI action goes through the same Control Fabric path as the CLI (same
     approval cards, same Work Log, same undo). The GUI never gets a private
     back door to root, and never calls ai-capabilityd directly (B9).
GP4  Every screen has: loading, empty, error, offline and permission-denied
     states; keyboard navigation; screen-reader names; dark/light; HiDPI.
GP5  Terminal-free guarantee (U382): all journeys in U261 are doable by mouse.

V4-C. "NOT A SINGLE TRACE OF FEDORA" - what that can and cannot mean (ZF)
--------------------------------------------------------------------------------
Aditya wants zero Fedora. Be precise about what is achievable (and do all of it):
ZF1  ACHIEVABLE AND REQUIRED = ZERO on anything a user can SEE or TYPE for
     identity: boot menu, UEFI boot entry label, Plymouth, SDDM, desktop, lock
     screen, About page, installer screens, app launcher entries, wallpapers,
     default bookmarks/start pages, `cat /etc/os-release`, `/etc/issue`, motd,
     hostname, `hostnamectl`, `rpm-ostree status` product label, `bootc status`
     product text, `neofetch`-style output, VMware VM settings. Proven by (a)
     rootfs scan, (b) OCR of every gallery screenshot, (c) boot-log scan.
ZF2  MUST REMAIN BY LAW/SAFETY (allowlisted with a written reason, U428):
     license texts, copyright headers, changelogs, package names/metadata of
     upstream packages (e.g. `rpm -qi bash` says Fedora Project as vendor),
     GPG keys used to verify upstream packages, SBOM entries, source URLs.
     Removing these would violate licenses or break security verification.
ZF3  CANNOT BE CHANGED WITHOUT REBUILDING UPSTREAM: the kernel release string
     (`uname -r` ends in `.fcNN`) and the EFI path `\EFI\fedora\` that Fedora's
     signed shim/GRUB expect. Rebuilding/re-signing the kernel or shim breaks
     Secure Boot trust. DEFAULT: leave them, label the UEFI boot entry
     "Directioner OS", document as residual (U435, U437). Aditya decides if a
     custom kernel build is worth it (it is a large separate project).
ZF4  NETWORK HOSTNAMES: upstream RPM mirrors/metadata live at fedoraproject.org
     and the base image at registry.fedoraproject.org. Directioner-hosted
     mirrors would mean publishing (B4). DEFAULT: our image updates come from a
     private registry; layered-package fetches still use upstream mirrors unless
     Aditya approves hosting (U445). Egress is listed honestly in Privacy.
ZF5  WORDING: nominative statements such as "built on open-source components
     including packages from the Fedora Project" may be legally required or
     permitted; U426 researches and cites the rules. Marketing copy never uses
     the Fedora name/logo as branding.
ZF6  The product claim is therefore: "no Fedora branding anywhere in the user
     experience", NOT "zero strings anywhere on disk". The purge report (U448)
     shows both numbers.

1. THE REALITY RULES (RR) - these override everything below
--------------------------------------------------------------------------------
RR1  REAL-EFFECT TEST (RET). A task is DONE only when a test boots the real
     image in a VM (QEMU/KVM or TCG), performs the action through the real
     path, and observes the effect with an INDEPENDENT tool (nmcli, flatpak
     list, rpm-ostree status, gsettings/kreadconfig, a screenshot, journalctl,
     busctl...). Unit tests against in-memory structs never close a task.
RR2  STATUS VOCABULARY. NOT-STARTED | SCAFFOLD (in-memory/mocked, labeled) |
     REAL-PARTIAL (works on the running image, gaps listed) | REAL-DONE (RET
     passed on main, CI run id attached). Never "DONE" without a RET log.
RR3  DONE EVIDENCE: commit hash on main + CI run id (green) + RET log under
     docs/evidence/<task>/ + screenshot for anything visual. Paste literal
     output. If cargo/CI/QEMU is unavailable in your shell, say so and mark
     the task UNVERIFIED - do not claim passing.
RR4  DON'T REIMPLEMENT THE OS. Integrate real components: bootc/rpm-ostree/
     greenboot, NetworkManager, BlueZ, PipeWire/WirePlumber, systemd/logind,
     UPower/power-profiles-daemon, firewalld, udisks2, flatpak, fwupd, CUPS,
     AccountsService, polkit, KDE/KWin D-Bus. A Rust struct that "models" one of
     them is SCAFFOLD. (Repeat offender: custom watchdog/slot controller.)
RR5  NO CUSTOM CRYPTO. Vetted libraries or OS facilities only (kernel keyring,
     Secret Service, TPM2 via tpm2-tss). In-memory only until done properly.
RR6  SIMULATION LABELING. Any mock/simulated module carries a top-of-file
     header "SCAFFOLD: no real OS integration" and appears in the mock register.
RR7  ONE TASK PER SESSION by default, then STOP; resume on "next". Aditya may
     write "run M1" (a whole milestone) or "run U040-U060"; that explicit
     instruction replaces the rhythm for that range only. Each task in the
     range still needs its own RET, and you STOP at the first red result.
RR8  WORK DIRECTLY ON MAIN (Aditya's standing instruction): small commits,
     clear messages with evidence, run fmt/clippy/test before each push, never
     force-push or rewrite history. No per-task issues/PRs/branches. Exception
     (safety): OWNER-AUTH and restricted-file changes are prepared as a patch
     under docs/owner-auth/<id>.patch with tests and NOT applied.
RR9  Status goes in docs/plan-status.md, updated in the same commit as the work.
RR10 If a real integration is impossible in the environment, write the exact
     blocker and the smallest next step. Never paper over it with a mock.

3. THE CONTROL FABRIC  (how "every OS function is visible to the CLI")
--------------------------------------------------------------------------------
Aditya's goal: the AI engineer can see everything the OS can do and control it
- Wi-Fi, settings, apps, files, services, kernel-level knobs. Delivered as:

   Directioner CLI / Aria / Qt shell / MCP clients
              |  (typed requests; never raw sockets to the root daemon)
              v
        directioner-intentd  (Intent Broker: auth, schema, origin, rate limit)
         |            |                         |
   OBSERVE plane   ACT-USER plane          ACT-SYSTEM plane
   directioner-    directioner-actd        draft -> Planner -> PolicyEngine ->
   statd           (runs as the user,      Reviewer -> Implementer (ai-
   (read-only      polkit-authorized       capabilityd, root, --exec) ->
   state tree)     D-Bus calls)            Verifier -> Work Log
         \             |                         /
          real system: NetworkManager, BlueZ, PipeWire, KWin/KConfig, logind,
          systemd, flatpak, rpm-ostree/bootc, firewalld, udisks2, fwupd, CUPS...

3.1 OBSERVE: statd exposes a read-only STATE TREE of the whole machine
    (network, bluetooth, audio, display, power, input, apps, services,
    packages/image, storage, users, security posture, settings, hardware).
    Everything in it is readable by the CLI/Aria subject to consent levels
    and redaction. No approval needed to read non-sensitive state.
3.2 DISCOVER: a machine-readable CAPABILITY CATALOG lists every action:
    id, params schema, scope (user/system), tier, preview, undo, backend used,
    status (REAL / SCAFFOLD / PLANNED). The CLI can enumerate it. The honest
    answer to an unsupported request is "not in the catalog" (+ how to add it).
3.3 ACT: every action = typed intent -> tiered by blast radius. Low-risk
    reversible user-scope actions can auto-run (once U171 is authorized).
    Anything destructive, privileged, boot/kernel/storage/firewall/user-account
    related is Confirm or ExpertReview and goes through the full pipeline.
3.4 EXPLAIN + UNDO: every action supports dry-run preview, an undo record where
    possible, and a Work Log entry (origin, who approved, result).
3.5 DEEP ACCESS WITHOUT RAW ROOT: "very deep" = typed capabilities down to
    sysctl, kernel modules, kernel args, systemd units, packages, boot, firmware.
    Unknown D-Bus methods are NOT callable generically; introspection is
    read-only for all, and a new method becomes callable only by adding a
    catalog entry (DESIGN-FIRST). That keeps reach wide and blast radius named.
3.6 COVERAGE IS MEASURED: a tool introspects the live image (busctl, systemd
    units, KConfig/gsettings keys, sysctl, /sys) and reports which functions
    are in the catalog and which are not (U087, reported in U110). The number is reported, not
    claimed.
